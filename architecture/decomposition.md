# Декомпозиция и взаимодействия

## 1. Про bounded context

| Способность | Субдомен | Bounded context / сервис | Язык, ответственность и инвариант |
|---|---|---|---|
| Управлять пользователями | Supporting; аутентификация — Generic | Customer / Customer Service | Пользователь, профиль, блокировка, право аренды. Один стабильный `userId`; профиль не содержит платёжных реквизитов |
| Управлять самокатами и разблокировкой | Core | Fleet / Fleet Service | Самокат, резерв, команда устройству, подтверждение замка. Один действующий резерв на самокат; команда открытия требует действующего резерва |
| Искать самокаты | Core | Discovery / Discovery Service | Доступный объект на карте, расстояние, свежесть. Это проекция для поиска, которая не гарантирует возможность аренды |
| Управлять поездками | Core | Rental / Rental Service | Поездка, попытка старта, завершение, нарушение, штраф. Не более одной незавершённой поездки пользователя |
| Назначать тарифы | Supporting | Pricing / Pricing Service | Тариф, версия, котировка. Принятая котировка неизменяема; опубликованные версии не переписываются |
| Принимать оплату | Generic — эквайринг; Supporting — внутренний учёт | Billing / Billing Service | Авторизация, списание, возврат, долг, платёж. Повтор команды не создаёт повторное списание |
| Управлять геозонами | Core | Geo Policy / Geo Service | Версия зоны, запрет движения, место парковки. Решение проверки содержит версию правил |

Разблокировка не выделена в отдельный сервис: резерв самоката, связь с устройством и подтверждение замка имеют один жизненный цикл и владельца. `Fine` принадлежит Rental: решение о нарушении связано с поездкой и доказательствами; Billing получает денежное обязательство, но не определяет нарушение. Тарифы отделены от поездок из-за собственного цикла публикации и возможности использовать последнюю опубликованную версию при отказе Pricing.

### Разные значения одного термина

- В Fleet `Scooter` — физический актив с техническим состоянием и резервом. В Discovery — карточка на карте. В Rental хранится `scooterId` и снимок существенных условий, а не общая ORM-модель.
- `Location` в Fleet — измерение устройства с временем и точностью; в Discovery — индексированная последняя позиция; в Rental — доказательство маршрута или парковки. Источник сырой телеметрии — Fleet, проекции и снимки принадлежат потребителям.
- `User` в Customer — профиль, в Billing — плательщик по `userId`; у Billing нет права редактировать профиль.
- `Tariff` в Pricing — версионированные правила; в Rental — неизменяемые условия конкретной поездки.

Общие идентификаторы не являются внешними ключами между БД. Нет общей доменной библиотеки и общей таблицы сущностей.

## 2. Владение данными и команды

| Команда | Сервисы | Исключительно принадлежащие данные |
|---|---|---|
| A — Клиент и аренда | Customer, Rental | Customer: `User`, RentalEligibility; Rental: `Trip`, `Fine`, состояния процесса старта, снимок тарифа и георешения, маршрут поездки |
| B — Парк и геоплатформа | Fleet, Geo, Discovery | Fleet: `Scooter`, `Location` (сырая телеметрия), Reservation, DeviceCommand; Geo: `Geofence`, версии политик; Discovery: SearchProjection, позиции и доступность для поиска |
| C — Монетизация | Pricing, Billing | Pricing: `Tariff`, Quote; Billing: `Payment`, PaymentAttempt, платёжные токены, учёт списаний/возвратов, задолженность |

Таким образом, все восемь исходных сущностей имеют владельца: User → Customer; Scooter и Location → Fleet; Trip и Fine → Rental; Tariff → Pricing; Payment → Billing; Geofence → Geo.

Одна команда владеет разработкой, миграциями, качеством данных, доступом, сроками хранения, релизами и дежурством своих сервисов. Три команды не означают три процесса. Discovery эксплуатируется командой B как самостоятельный сервис из-за особой нагрузки. Дополнительная платформенная команда не предполагается: общие шаблоны CI/CD, брокер и наблюдаемость обслуживаются тремя командами с назначенными ответственными; владелец эксплуатации брокера — B, входного API — A.

У каждого сервиса приватная БД/схема и отдельные учётные данные. Только владелец пишет и выполняет миграции. Физический кластер допустимо разделять на старте, но тяжёлые геозапросы и платежи желательно разнести для изоляции ресурсов. Чужие данные доступны через контракт или локальную проекцию, без прямого SQL. Проекция не становится вторым источником истины. Персональные координаты имеют ограниченное хранение и доступ; удаление профиля согласуется с независимыми обязательствами хранения финансовой истории.

Например, Rental → Fleet — запрос резервирования и управления замком, Fleet → Rental — подтверждение результата. Это обзор бизнес-взаимодействий без протоколов, БД и инфраструктуры; технические детали показаны на C2.

На карте представлены семь контекстов. Разблокировка входит в управление парком, штрафы — в управление поездками. Внешний платёжный провайдер и устройства показаны на C1/C2, чтобы карта предметной области оставалась простой.

Отношения DDD уточняются текстом: внутренние поставщики согласуют контракты с потребителями (Customer/Supplier), публикуют версионированные API и события (Open Host Service / Published Language). Discovery принимает факты Fleet и Geo для собственной проекции (Conformist). ACL внутри Billing и Fleet переводят внешние статусы провайдера и оборудования в доменные состояния. Эти обозначения не вынесены на стрелки, чтобы сохранить формат примера задания. Нет общей канонической модели или Shared Kernel.

## 4. Основные взаимодействия

| Инициатор → получатель | Контракт | Назначение |
|---|---|---|
| Приложение → Discovery | REST `GET /scooters/nearby` | Карта без синхронного обхода остальных сервисов |
| Rental → Pricing | REST `POST /quotes` | Зафиксировать цену перед началом; допустим локальный расчёт по актуальной опубликованной версии |
| Rental → Geo | REST `POST /zone-checks` | Проверить начало/парковку; допускается локальная проверка по действующей версии |
| Rental → Fleet | REST резервирования | Атомарно занять конкретный самокат, проверить актуальное состояние |
| Rental → Billing | Kafka `AuthorizePayment`, `CapturePayment`, `VoidAuthorization` | Платёжные шаги процесса, без блокировки пользовательского HTTP-запроса |
| Billing → Rental | Kafka `PaymentAuthorized`, `PaymentDeclined`, `PaymentCaptured`, `PaymentFailed` | Продолжить процесс или записать задолженность |
| Rental → Fleet | Kafka `UnlockScooter`, `LockScooter`, `ReleaseReservation` | Команды с `operationId`, `tripId`, `reservationToken` |
| Fleet → Rental | Kafka `ScooterUnlocked`, `ScooterLocked`, `DeviceCommandFailed` | Подтверждённый результат физической операции |
| Fleet → Discovery, Rental | Kafka `ScooterStateChanged`, `LocationUpdated` | Поисковая проекция и привязанный к поездке маршрут |
| Geo → Discovery, Rental | Kafka `GeofencePublished` | Версионированные локальные правила; на карте — зоны |
| Pricing → Rental | Kafka `TariffPublished` | Локальные опубликованные правила расчёта |
| Customer → Rental | Kafka `RentalEligibilityChanged` | Локальная проекция блокировок и права аренды |
| Rental → Billing | Kafka `TripChargeRequested`, `FineAssessed` | Сумма, валюта, основание и идентификатор обязательства |
| Billing ↔ PSP | HTTPS API и подписанные webhooks | Авторизация, списание, сверка; ACL внутри Billing |
| Fleet ↔ устройства | MQTT/TLS, подтверждения | Телеметрия и управление замком; ACL внутри Fleet |

### Поиск

Discovery фильтрует геоиндекс по радиусу, последнему состоянию и возрасту телеметрии. В ответе есть `observedAt`. Проектная гипотеза: скрывать самокаты без обновления более 30 секунд; потребительский лаг проекции — до 5 секунд. Найденный самокат может оказаться занят: окончательное решение принимает транзакция резерва Fleet, а интерфейс обрабатывает `409 Conflict`.

### Начало поездки: сохраняемый процесс в Rental

1. Клиент отправляет `POST /trips` с `Idempotency-Key`. Rental проверяет подпись действующего токена локально, право аренды и отсутствие незавершённой поездки. Уникальное ограничение по пользователю защищает от параллельных стартов. Для обычного допуска используется свежая проекция Customer; её проектный предел возраста — 60 секунд, иначе запрос к Customer, а при его отказе новый старт отклоняется. Это допускает задержку обычной блокировки до 60 секунд; срочная блокировка требует отдельного подтверждённого распространения или онлайн-проверки.
2. Rental сохраняет `STARTING`, котировку/снимок тарифа и версию геоправил. Получает резерв Fleet с lease и fencing token. В Fleet условное обновление/уникальное ограничение исключает двойную аренду. HTTP возвращает `202` и `tripId`; результат читается через `GET /trips/{id}`.
3. Rental публикует `AuthorizePayment`; Billing создаёт авторизацию у PSP с ключом операции. `PaymentAuthorized` переводит процесс к разблокировке; отказ освобождает резерв. Lease продлевается только для живого процесса. До отправки unlock авторизация и резерв должны быть действующими.
4. Fleet проверяет fencing token и отправляет команду устройству. Только подтверждение устройства позволяет Rental перейти в `ACTIVE`. Запись времени открытия Fleet используется как начало тарификации; подтверждение содержит идентификатор и время операции.
5. При тайм-ауте результат считается неизвестным. Выполняется сверка устройства/PSP по исходному ключу, а не новая независимая операция. После подтверждённого отказа запускаются отмена авторизации и освобождение резерва. Задержавшийся ответ об открытии переводит самокат в сверку/карантин и инициирует безопасную блокировку, а не выдачу другому клиенту.

Fleet не возвращает самокат в `AVAILABLE` только по истечению lease, если команда открытия уже отправлена или состояние замка неизвестно. Устаревший fencing token не может открыть новый резерв. Для реального устройства необходима поддержка дедупликации команд либо проверка состояния в адаптере; если этого нет, гарантия слабее, а неопределённые самокаты изолируются.

### Завершение и расчёт

1. Rental принимает идемпотентный запрос завершения и проверяет парковку по версии Geo; при явном запрете предлагает разрешённое место. При неизвестной позиции/правилах фиксирует `FINISH_PENDING` и обращение на проверку, без автоматического штрафа.
2. Rental отправляет команду закрытия, Fleet получает подтверждение замка и положение устройства. Rental фиксирует `COMPLETED` и время подтверждённого закрытия, вычисляет сумму по сохранённым условиям и создаёт денежное обязательство. Fleet освобождает самокат только после подтверждённого завершения, по `ReleaseReservation`; при незавершённой сверке самокат недоступен.
3. В одной транзакции Rental сохраняет результат и outbox-запись `TripChargeRequested`; Billing списывает сумму из авторизации либо согласует дополнительное списание. Состояние оплаты хранится отдельно от состояния физической поездки. При отказе PSP поездка остаётся завершённой, платёж — `PENDING`/`FAILED`, долг — в Billing; дальнейший старт требует успешной авторизации и отсутствия подтверждённого долга.
4. Rental определяет штраф только по проверенным данным и версии правила, сохраняет основания и публикует `FineAssessed`. Отмена штрафа создаёт корректировку/возврат с отдельным ключом, не удаляет историю.

Тайм-аут завершения не доказывает, что самокат открыт: сверяется фактическое время замка. При подтверждённом более раннем закрытии стоимость пересчитывается/корректируется. Без подтверждения интерфейс показывает ожидание и путь обращения в поддержку.

### Доставка и согласованность

Локальные ACID-транзакции охраняют инварианты одного владельца. Между сервисами — eventual consistency и saga старта/завершения в Rental. Это ограниченный доменный координатор, а не общая бизнес-шина. Остальные проекции обновляются хореографией.

Изменение данных и outbox фиксируются одной транзакцией. Доставка at-least-once: каждый потребитель использует inbox/уникальный `eventId`, а бизнес-команды — устойчивый ключ операции. Конверт: `eventId`, `aggregateId`, `aggregateVersion`, `occurredAt`, `schemaVersion`, `correlationId`. Порядок сохраняется в пределах агрегата/ключа партиции; старые версии игнорируются, разрывы запускают сверку. Для Location используются номер измерения и время, поздняя точка не заменяет более новую позицию.

Повторы имеют ограничение, exponential backoff и jitter; после исчерпания — DLQ, оповещение и управляемое повторение. Для PSP неоднозначный ответ сначала сверяется по ключу. Exactly-once между БД, брокером и внешним оборудованием не заявляется. Публичные API/события развиваются обратно совместимо, обязательные изменения проходят версионирование и consumer contract checks.

## 5. Изоляция отказов

| Отказ | Сохраняемая функция | Ограничение/восстановление |
|---|---|---|
| Внешний PSP | Поиск, просмотр истории, завершение активной поездки | Новые старты без успешной авторизации запрещены; списания накапливаются в outbox/очереди, затем сверяются и повторяются |
| Pricing | Активные поездки считаются по снимку; новые — по действующей опубликованной версии | При отсутствии подходящей версии новые старты запрещены |
| Geo | Локальная проверка по действующей версии, поиск и история | Для новых стартов версия должна укладываться в проектный предел свежести 5 минут; иначе отказ. Для завершения используются действующие локальные правила, а при неопределённости — FINISH_PENDING и проверка |
| Discovery | Уже начатые поездки, их завершение | Новая карта недоступна; нет обхода через массовые вызовы Fleet |
| Customer | Поиск и завершение; старт с действующим токеном и свежим допуском | Вход/обновление токена и допуски без свежей проекции недоступны |
| Fleet/связь устройства | История, тарифы, карта со скрытием устаревших объектов | Старт/подтверждение замка невозможны; операция остаётся ожидающей, нужна сверка |
| Kafka | Чтение локальных данных, приём сохраняемых запросов в пределах лимита | Saga не продвигается; ответы pending. Ограничить backlog, при переполнении отклонять новые операции, не накапливать бесконечно |
| Rental | Поиск, профили и просмотр тарифов | Управление поездками недоступно до восстановления; реплики и БД с failover уменьшают окно отказа |

Для сетевых вызовов — тайм-ауты, circuit breaker и раздельные пулы ресурсов; bounded queues и backpressure защищают от каскадного исчерпания. Gateway не выполняет длинную оркестрацию. Токены проверяются локально по кэшированным ключам с ограничением срока действия. Отказ критического сервиса может лишить конкретного сценария, но не всех функций системы.

## 6. Масштабирование и проверка нагрузки

Рабочая гипотеза для пиковых 5 000 клиентских RPS: 3 500 — поиск (70%), 750 — чтение поездок (15%), 250 — команды поездок (5%), 250 — профили (5%), 250 — тарифы и прочие чтения (5%). Сумма — 5 000. Это не RPS каждого сервиса: резервирования, события и обращения к PSP создают дополнительную внутреннюю нагрузку. Телеметрия не включена в эти 5 000.

Discovery масштабируется по RPS/latency и геопартициям, Fleet — по потоку устройств и задержке команд, Rental — по командам и числу активных saga, Billing — по лагу/лимитам PSP. Реплики HTTP-сервисов stateless; состояние операций сохраняется в БД. Число Kafka-потребителей ограничено партициями; порядок одного самоката/поездки не распараллеливается произвольно. Геопроекции можно восстанавливать из снимка и потока, резервирование всегда идёт к владельцу.

Объём телеметрии: `N_online / interval_seconds` событий/сек. Например, **условные** 100 000 онлайн-самокатов раз в 10 секунд дают 10 000 событий/сек сверх API. Требуются фактические N, размер события, срок хранения и коэффициент репликации. 5 млн пользователей не означают 5 млн онлайн-клиентов и не определяют число реплик.

План проверки: нагрузить реалистичной смесью 5 000 RPS плюс отдельный профиль телеметрии; измерить p95/p99, ошибки, задержку outbox/проекций, блокировки БД и backlog. Проверить параллельный старт одного самоката/пользователя, повтор платежа, позднее открытие, падение PSP и брокера, восстановление проекции. Целевые значения и запас мощности согласуются до теста; производительность по диаграмме не гарантируется.

## 7. Почему именно такие границы

Высокая cohesion: переходы физического состояния и резерв — в Fleet; жизненный цикл аренды и нарушение — в Rental; денежный учёт — в Billing. Нет отдельных CRUD-сервисов для Location, Fine и Unlock. Низкая coupling: карта не вызывает весь граф сервисов на каждый запрос; тарифы и геозоны распространяются версиями; сервисы не читают чужие таблицы. Изменение геополитики или тарифа обычно требует изменения владельца, а не синхронного релиза всех сервисов.

Проверка границ по лекции: новое правило штрафа меняет Rental; новый PSP — ACL Billing; новый протокол замка — ACL Fleet; новый способ ранжирования карты — Discovery. Изменение публичного смысла тарифа может затронуть Pricing и Rental: это реальная семантическая связь, поэтому контракт версионируется. Деплой каждого сервиса должен проходить при совместимых старых версиях соседей.

## 8. Потенциальные проблемы

- Распределённая согласованность: фантомная доступность на карте, задержка блокировок, устаревшие зоны. Нужны метки свежести, версии, повторная проверка у владельца.
- Неопределённый результат физических и платёжных команд. Нужны сверка, карантин, компенсации и ручной разбор; сетевой тайм-аут не равен отказу операции.
- Компенсация может сама не выполниться. Saga хранит прогресс, повторяет шаги и сигнализирует о зависших операциях.
- Семь сервисов и инфраструктура создают нагрузку на три команды. Нужны унифицированные шаблоны эксплуатации; дальнейшее дробление без измерений не оправдано.
- Kafka, Gateway и общие физические кластеры могут стать общими точками отказа. Нужны реплики, квоты и независимые пулы; резервное копирование без проверенного восстановления недостаточно.
- Геораспределение, «горячие» городские партиции, рост истории и персональные координаты требуют отдельных решений по шардированию, хранению и доступу после измерений.
- Ошибочные координаты не должны автоматически приводить к штрафу: сохраняются точность и версия правила, доступен разбор доказательств.
- Контракты могут превратиться в скрытый общий релиз. Проверять независимые релизы, число совместных изменений, DORA, MTTR и лаги; целевое число прямых обращений к чужим БД — ноль.
